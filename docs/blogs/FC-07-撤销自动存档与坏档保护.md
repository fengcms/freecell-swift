# FreeCell 开发实战 FC-07｜撤销、重做与自动存档：让每一步都能回来

**本文目标**：说明游戏历史、自动收牌和存档如何协同工作，并复盘一个重要的数据保护问题：坏档无法备份时，后续写入必须停下来，不能用新局覆盖原始文件。

---

## 一、牌局历史不是一串按钮回调

`GameArchive` 保存初始局面、当前局面、历史条目和游标。每次成功操作记录 `before`、`after` 与可选 `Move`；撤销让游标回退并恢复前态，重做则恢复后态。若撤销后做了新动作，旧游标之后的重做分支会被截掉。

重开和新局也不同：重开回到当前牌局的初始发牌，清空历史并重置计时；新局则生成新的种子和发牌。历史模型把这些用户能感受到的行为变成明确状态，而不只是界面按钮行为。

## 二、自动收牌应该属于哪一次操作

用户把牌移到某列后，如果开启自动安全收牌，规则可能顺便把几张牌移入基础堆。若每收一张都建立单独历史，撤销会需要连续按很多次，体验不自然。

因此一次玩家操作和由它触发的安全收牌合并为一个历史步骤。规则可以生成多个中间局面供动画播放，但最终状态只提交一次。手动“收牌”也把整批安全收牌作为一步，所以操作、动画和撤销边界一致。

## 三、定期写入与原子替换

会话定时把编码后的牌局写入 Application Support。保存工作由 actor 串行处理，并带修订号；较旧的异步写入不能盖过较新的状态。写文件采用原子写入，减少进程中断时留下半份 JSON 的风险。退出时还会等待最后一次保存结果。

这些机制解决正常写入的顺序和完整性，却不能替代恢复策略。读档失败时，应用会尝试把无法读取的文件移到 `unreadable-*.json` 备份，再建立新局继续工作。

## 四、坏档备份失败是另一种状态

如果移动备份也失败，应用不能假装问题不存在并继续定时写入。否则新牌局可能覆盖仍有恢复价值的原始坏档。项目代码审查专门指出这条边界：保护不能依赖某句错误文案，因为文案可能改语言、改措辞；它应该是明确的内部状态。

修正后，`archiveWritesBlocked` 表示本次会话禁止任何牌局写入。设置语言、动画或声音不会触发存档写入；新局、重开、撤销、定时保存和退出保存也都会尊重该状态。即使界面错误提示未来翻译成其他语言，数据保护逻辑仍不受影响。

## 五、偏好和牌局存档分开

语言、动画速度、自动移动手势、音乐和声音开关属于应用偏好；当前牌局、历史、计时则属于牌局存档。将两类数据分开能避免用户调整界面语言时，意外重写整份牌局文件。

自动收牌偏好有一个兼容字段也保存在 archive 中，它决定已存档牌局恢复后的行为。因此只在这个字段实际变化时同步写入牌局；其他设置只存自己的偏好域。

## 六、用失败注入验证原文件没被覆盖

普通成功路径无法证明保护有效。回归检查构造一个损坏文件，并注入“备份失败”；随后修改多个设置、创建新局、重开、撤销、重做、暂停、计时和退出保存。最后逐字节比较原文件，确保它仍与最开始一致。

同一检查也验证正常存档仍能保存、语言修改不会改写牌局文件。这是针对风险的集成测试：验证真实 `GameSession` 行为，而不是仅测试一个孤立的布尔变量。
