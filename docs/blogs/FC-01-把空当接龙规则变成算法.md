# FreeCell 开发实战 FC-01｜把空当接龙规则变成状态与算法

**本文目标**：把玩家熟悉的空当接龙规则，转换成可以由程序验证的状态模型和移动算法。重点解释工作列接牌、临时空位、整组移动容量，以及为什么“整组拖过去”仍需要单牌级别的合法性证明。

**前置知识**：了解纸牌的花色、点数，以及空当接龙的基本玩法。无需先阅读 Swift 代码。

---

## 一、先把牌局描述成数据

一副牌有四种花色、每种花色十三个点数。牌局包含三类位置：

- 八个工作列，每列按从底到顶的顺序保存纸牌；
- 四个空当，每个最多放一张牌；
- 四个基础堆，每个花色从 A 开始，按点数递增。

核心模型不需要知道窗口、图片或鼠标坐标。它只关心牌在哪里，以及一个移动能否改变局面。代码中的 `GameState` 正是这份局面：`tableau`、`cells` 和 `foundations` 分别代表三类位置。

这层分离非常有用。界面可以用点击、拖拽或双击发起动作，但最后都构造成同一种 `Move`，交给规则函数检查。鼠标手势不会拥有一套“自己的规则”。

## 二、工作列的接牌规则

一张牌可以压到另一张牌上，需要同时满足：颜色相反，且来牌点数恰好小一。

例如，黑桃 7 可以接到红桃 8 或方块 8 上；它不能接到梅花 8，也不能接到红桃 9。A 与 K 不循环连接，所以 K 上不能接 A。

多张牌一起移动时，源位置上被选中的牌必须已经组成一条合法牌龙：从底到顶，点数逐张递减、颜色红黑交替。整组的底牌还必须能接到目标列最上面的牌上。目标列为空时，合法牌龙可以直接移过去。

在实现里，这两条规则拆成小函数：`canStack` 检查两张牌之间的关系，`isOrdered` 检查一段牌是否连续有序。小函数让单牌移动、整组移动和自动动作共享相同判断。

```swift
public static func canStack(_ card: Card, on target: Card) -> Bool {
    card.suit.isRed != target.suit.isRed
        && card.rank.rawValue + 1 == target.rank.rawValue
}
```

## 三、空当和空列决定一次能搬几张

FreeCell 允许一次移动一整组牌，但这个动作在逻辑上等价于使用空当和空列逐张搬运。若有 `F` 个空当、`E` 个可用空列，最多可以移动：

```text
(F + 1) × 2^E 张
```

这里的空列不包括源列和目标列。目标列如果为空，它就是落点，不能同时充当中转列。源列当然也不是空出来供自己使用的中转空间。

为什么会有这个公式？只有空当时，每个空当能暂存一张，最后一张可以直接落到目标，所以容量是 `F + 1`。每增加一个中转空列，可以把可暂存的牌组再递归分拆一次，容量翻倍，因此乘上 `2^E`。

举例：若有 1 个空当和 2 个可用中转空列，理论容量为 `(1 + 1) × 2² = 8` 张。目标列为空时，那个目标不会计入 `E`；可用空间可能因此少一倍。很多看似“游戏有 bug”的长拖动问题，实际是玩家把落点也当成了中转列。

代码把计算集中在 `capacity(from:to:in:)`，规则验证则拒绝超过容量的移动。视图即使允许用户拖动一整组，最终仍不能绕过这个检查。

## 四、用逐张移动给公式做见证

公式提供上限，但单看公式还不够。项目还实现了 `singleCardMoves`：给定一个合法整组移动，它会构造一串只移动单张牌的步骤，逐步借助空当和中转列把牌组搬过去。

这是一种很实用的验证方式：我们不只是声称“这组牌应该可以移动”，而是能生成一个合法的逐张操作序列作为见证。自动检查可以再对这个序列逐步应用规则，确保每一步都合法，最后抵达整组移动的目标局面。

递归拆分的直觉是：先把一部分牌移到临时空列，再把余下部分移至目标，最后把临时列中的牌接回目标。剩余的空列和空当决定每次递归能处理的子问题大小。

## 五、基础堆和可逆的用户需求

基础堆只能按花色从 A 向 K 建立。放牌时，必须是对应花色的下一张牌。游戏支持自动收牌，但只有规则判断安全时才收，避免过早把仍有用的低点数牌锁在基础堆。

这个项目还允许把基础堆最上面的一张牌移回工作列。这是一个产品选择。实现上，源可以是 `.foundation(suit)`，但移动数量必须为一，目标必须是工作列，并且仍然要通过目标列接牌规则。规则层不需要为这个需求开后门。

## 六、规则函数尽量不修改输入

`validate` 负责判断动作是否合法，`applying` 先验证，再在局面副本上完成移动并返回新状态。非法动作会抛出错误，不会留下“牌已经从源列拿走、但目标位置拒绝接收”的半成品局面。

这种“先验证，再产生新状态”的方式也让撤销、重做和存档验证更直接：每一步都能明确表达为前后两个完整局面。

## 七、提示是启发式，不是假装会解题

游戏中的提示会对合法移动打分，例如优先推荐安全收牌、把牌从空当放回工作列，或移动完整牌龙。但它只是局部启发式，没有搜索完整状态空间，也不证明整局必定可解。

把这点说清楚很重要。玩家点了“提示”，期待的是一个有意义的下一步；如果把启发式描述成“求解器”，用户就会以为它能保证胜利。界面和文档应准确描述功能边界。

## 八、把规则转成测试场景

规则验证覆盖常见动作，也覆盖容量边界、乱序牌组、非法目标、空位耗尽、A/K 不循环、基础堆取回和完整胜利。随机合法操作还会反复检查牌局不变量，确保每张牌始终只出现一次。

更重要的是，测试应该围绕玩家可观察的行为组织：超容量的动作必须拒绝；合法动作之后 52 张牌仍完整；撤销再重做能回到相同状态。公式、模型和测试互相支撑，规则才真正从“大家都知道”变成了程序可以信任的部分。
