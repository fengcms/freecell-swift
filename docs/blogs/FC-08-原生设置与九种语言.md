# FreeCell 开发实战 FC-08｜设置也属于产品体验：快捷键、声音与九种语言

**本文目标**：介绍一款小型 macOS 游戏如何接入用户熟悉的设置入口、菜单和快捷键，并把多语言做到即时切换，而不是只翻译几个按钮。

---

## 一、像 macOS 应用一样打开设置

玩家习惯用 ⌘, 打开偏好设置，因此游戏使用系统 Settings 场景，并通过应用菜单和牌桌齿轮入口访问。设置分为操作、动画与声音、界面和声音来源：自动安全收牌、双击或右击、自动移牌时优先使用空当或空列、动画速度、背景音乐、移动音效、界面语言和功能按钮快捷键。

偏好独立保存，启动后恢复；切换它们不会重置牌局。声音来自明确署名或许可的素材：Dream Culture 背景音乐按 CC BY 4.0 标注，Kenney 移牌音效按 CC0 标注。应用暂停或失去焦点时暂停音乐，设置里能单独关闭音乐和音效。

## 二、语言设置不是只给 SwiftUI 一个 Locale

项目支持英语、简体中文、繁体中文、法语、德语、西班牙语、阿拉伯语、日语和韩语。用户可手动选语言，也可跟随系统首选语言；系统首选语言不在支持范围时回退英语。手动选择立即生效并保留到下次启动。

只设置 SwiftUI 的 `Locale` 不够。游戏还有 AppKit 自绘的牌名、动态状态文字、原生菜单和独立 About 窗口。`GameLocalization` 负责运行时查词与格式化；SwiftUI 环境使用相同语言；原生菜单标题和 About 窗口标题也需要刷新。

## 三、动态消息要保留变量

像“已选择黑桃 Q”“已移动到第 3 列”这样的状态不是固定字符串。若在界面里用中文短语做正则替换，一旦数字、花色或文案稍有变化，译文就可能断掉。

这个项目将核心规则错误和牌局消息保留在规则/会话层，在界面边界进行本地化，并为动态消息提供带参数的模板。覆盖检查会验证每种语言都有对应文案、格式占位符数量相符，并检查牌名、位置、移动次数、提示和容量等消息能正确渲染。

这套方案仍有改进空间：将来可把动态消息从自然语言匹配进一步迁移到结构化消息键。当前实现重点是兼容现有状态文本并用运行时目录覆盖九种语言，审稿时应明确这种取舍，而不要把它说成最理想的长期架构。

## 四、阿拉伯语带来的布局问题

阿拉伯语使用从右向左的文字方向。SwiftUI 设置和文字视图会响应 RTL，但纸牌列的物理顺序、牌面图片及键盘方向映射应保持稳定，不能因为文字方向变化而把第 1 列悄悄镜像到另一侧。

因此 RTL 应用在文字布局层，牌桌维持既定空间坐标。阿拉伯语界面要检查设置标签对齐、按钮顺序和文本阅读方向，同时确认纸牌列顺序保持一致。

## 五、关于窗口和系统菜单的边界

关于窗口用 SwiftUI 绘制，但由独立 AppKit 窗口控制器管理。语言切换时，正文通过可观察的本地化状态更新，标题由控制器主动刷新。macOS 系统菜单由系统创建，项目会重新本地化常用菜单项；系统控制本身的辅助说明仍可能遵循系统语言。

这说明“整个应用都翻译了”需要逐类说明边界：主界面、状态、菜单、确认框、设置、规则和辅助功能牌名属于应用；操作系统管理的输入法、系统安全提示或窗口控制辅助文案则由 macOS 决定。

## 六、语言完整性和人工审校是两回事

自动检查可以保证目录结构完整、占位符成对、动态消息能被格式化；它不能判断法语是否自然、日语是否礼貌、阿拉伯语是否符合母语表达。项目的九语言覆盖有自动检查和界面验收，但译文尚未经过所有语言母语者审校。

把这个限制写出来，比宣称“完整专业本地化”更诚实。界面可用性和语言质量是两类质量，需要不同的验证方式。
