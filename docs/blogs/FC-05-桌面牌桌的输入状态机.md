# FreeCell 开发实战 FC-05｜点击、双击、拖拽和整组移动：桌面牌桌的输入状态机

**本文目标**：讲解同一张牌如何响应单击、双击、右击和拖动，以及这些手势怎样共享一套规则。重点复盘双击延迟和长按边界这类只有真实操作才容易发现的问题。

---

## 一、一个鼠标按下不一定就是一个点击

如果单击立即提交，而第二次点击又触发自动移动，那么双击会先执行一次单击，再执行一次自动动作。第二个动作发生时，牌的位置可能已经改变，结果会让玩家觉得双击不稳定。

因此，双击模式下单击不会立刻提交。鼠标抬起后，牌桌暂存一次待处理点击，并等待系统双击间隔；期间如果同一张牌出现完整第二次点击，就执行自动移牌，否则到期后才提交第一次单击。快速点击不同位置时，前一次待处理点击先完成，再开始新的交互。

## 二、为什么系统 clickCount 不够

初版曾在第二次按下时根据系统 `clickCount` 判断双击。但第二次按下和第二次抬起可能跨越系统双击时间：用户先快速按下，再按住鼠标，之后才松开。如果只在按下时认定双击，自动移牌仍会在长按后执行。

修正后，牌桌比较第一次按下到第二次抬起的完整时间，并确认两次都指向同一张牌。第二次按下到抬起之前，第一次单击仍保留；如果抬起时已超时或发生在牌外，就只提交第一次单击，不触发自动移动。

鼠标拖动是另一条路径。移动超过阈值后，取消待处理单击，确认源牌可以选中且牌组有序，再创建拖动预览。放开鼠标时还要检查牌局版本，避免用户在拖动期间暂停、重开或改变窗口后，旧拖动误提交。

## 三、整组拖动是视觉动作，规则仍逐一验证

拖动一组牌时，视图隐藏来源中的整组牌，在鼠标位置绘制完整、不透明的牌龙，并保持原来的叠放间距。鼠标释放到目标列后，不逐张模拟 GUI 操作，而是提交一个 `Move`，其中包含源、目标和牌数。FreeCellCore 再检查牌龙顺序、目标接牌规则和容量。

这样既满足玩家“一次拖一整组”的期待，也保留了规则模型的简单性：撤销时是一笔操作，存档时是一条历史，规则验证不依赖绘图过程。

## 四、手势选择属于偏好，不是规则分叉

设置允许玩家选双击或右击作为自动移牌手势。右击直接走 AppKit 右键事件，不弹系统菜单。回车仍可自动移动。无论入口是哪一种，最后都调用同一个 `Rules.automaticMove`，所以优先级不会因手势改变。

工作列牌的自动目标先搜索基础堆和可接牌的非空列，再依“空位优先级”设置尝试空当或空列；同类目标从左向右。默认优先空当以保留空列，玩家也可以选择优先空列。基础堆顶牌取回时会跳过空当，优先回到工作列，避免把牌从一个暂存位置换到另一个暂存位置。

## 五、点击焦点和可见区域

牌桌不会在启动时随意激活某个位置。点击空白处可以清除焦点；移动完成后焦点应落到目标列最后一张牌。叠牌命中遵循实际暴露的牌面区域，绘制顺序靠上的牌先参与命中检查。

这类行为容易在鼠标回调中零散出现，所以需要把可见几何集中起来。牌桌项目中的 `visibleFrame` 被鼠标命中、抬起检查和辅助功能边界复用，避免同一张牌在视觉与操作上有不同边界。

## 六、不要只验证“能拖过去”

输入验收需要分别覆盖：单击选择与取消、双击优先级、不同目标、无合法目标、牌龙边界、空列释放、基础堆取回、拖动中取消，以及超时长按。每种事件的先后顺序都可能影响状态，因此，除了规则检查，也需要在真实桌面上体验鼠标时序和反馈。

真实试玩带来的最重要经验是：输入不是几个独立按钮，而是一段事件序列。鼠标何时按下、何时抬起、期间有没有拖动、牌局是否已经变化，都决定最终动作。把它当成小型状态机来设计，比不断追加 `if clickCount == ...` 更可靠。
