# FreeCell 开发实战 FC-02｜SwiftUI 不够时怎么办：Swift Package、AppKit 牌桌与职责边界

**本文目标**：介绍这个原生 macOS 游戏如何组织 Swift 工程，以及为什么界面主要使用 SwiftUI，精细牌桌则通过 AppKit 实现。读完后，你会看到怎样把规则、布局与平台界面分开，让项目既能使用系统能力，也能独立验证核心逻辑。

**前置知识**：熟悉 Swift 基础即可。不了解 AppKit 也可以先看职责划分。

---

## 一、不是所有界面都要用同一种框架

SwiftUI 很适合组织应用窗口、工具栏、设置表单、菜单入口和说明文字。它的状态驱动写法也让很多常规界面简单直观。但纸牌桌有一些更细的需求：自定义纸牌绘制、鼠标按下与抬起的时序、整组拖动的实时预览、重叠牌的可见区域命中、胜利序列动画，以及键盘焦点管理。

因此，项目没有在“全 SwiftUI”和“全 AppKit”之间二选一：主窗口和常规控件用 SwiftUI；牌桌使用 AppKit `NSView`，并通过 SwiftUI 的代表器接入应用。这是一个局部边界——只有需要低层输入和绘制控制的区域使用 AppKit。

## 二、三个模块，各自负责一件事

工程使用 Swift Package，主要分成三层：

| 模块 | 职责 | 例子 |
|---|---|---|
| `FreeCellCore` | 牌、位置、局面、规则、发牌和存档模型 | `Card`、`GameState`、`Rules`、`GameArchive` |
| `FreeCellPresentation` | 不依赖具体窗口的布局、动画时间线与偏好模型 | `BoardLayout`、`BoardMotion`、`GamePreferences` |
| `FreeCellApp` | SwiftUI/AppKit 应用界面、音频、窗口、会话和资源加载 | `GameView`、`GameBoard`、`GameSession` |

核心规则模块不导入 SwiftUI 或 AppKit。它不知道牌面如何显示，也不知道用户双击了鼠标还是按下了键盘。这样的隔离让规则可以在没有启动应用界面的情况下运行检查。

呈现模块再放置一些需要图形坐标、但不属于游戏规则的模型。例如，`BoardLayout` 根据窗口尺寸计算牌宽、牌列位置和拖放目标；`BoardMotion` 描述动画各阶段的坐标与时长。它们描述“如何呈现”，而不决定“某次移动是否合法”。

应用层负责将用户输入转换为移动请求，交由规则核心处理，再把新状态交给牌桌显示。声音、偏好、原生窗口配置和本地化也留在应用层，避免核心模型承担平台服务职责。

## 三、会话对象负责协调，而不是发明规则

`GameSession` 位于应用层，管理当前牌局、交互状态、撤销/重做、计时、设置与保存。它接收“把这几张牌从这里移到那里”的请求，调用 `Rules` 验证和生成新状态，再更新历史并安排显示反馈。

这条路径的重要之处是：会话可以协调很多功能，但合法性仍由单一规则实现决定。点击、拖拽和双击最后都进入同一套规则。这样可以避免“拖拽允许、双击不允许”之类的规则分叉。

存档写入则交给后台 actor 串行处理，并附带修订号，防止较慢的旧写入覆盖较新的牌局。异步保存与主线程界面职责不同，因此也有清晰边界。

## 四、牌桌为何使用自定义 NSView

牌桌不是传统表格。每张牌可能压住下一张牌的一部分，鼠标点击暴露区域需要命中对应纸牌；拖动时要隐藏原位牌组，在同一个视图中绘制完整、不透明的牌龙；动画还要让多张牌保持相对间距。

自定义 `NSView` 给了项目直接处理这些事件的空间：

- 根据鼠标坐标寻找最上层可见纸牌；
- 跟踪按下、移动、抬起，区分点击、双击和拖拽；
- 在原牌桌坐标系中绘制拖动预览；
- 控制键盘焦点及辅助功能元素；
- 根据游戏状态执行增量重绘。

这不是说 SwiftUI 做不到任何一项，而是当这些细节集中出现时，一个小型 AppKit 视图更容易明确输入顺序和绘制行为。边界也因此保持有限：工具栏、设置和常规文案仍由 SwiftUI 处理。

## 五、资源和应用包也有边界

扑克牌 PNG、音频、图标和翻译目录作为应用资源打包。加载资源时通过 bundle 查找，而不是依赖开发机器上的绝对文件路径。这样开发构建和最终 `.app` 使用相同资源入口。

应用发行还会检查实际包结构：主程序、Swift Package 资源 bundle、牌面、音频、图标和第三方声明都必须在应用包中。仅仅“本机能跑”并不能说明一个独立下载的应用包含了所有资源。

## 六、分层不是为了目录好看

模块划分只有在减少耦合时才有价值。这个工程里，分层解决了几件具体事情：规则可脱离 UI 检查；布局可以用尺寸输入输出测试；AppKit 输入代码集中在牌桌；应用资源可以跟着包发布；用户偏好不会污染核心牌局模型。

如果只是把代码按文件夹拆开，却继续让规则读取窗口状态、让界面自行判断合法性，那并没有得到真正的边界。判断标准很简单：改动画时是否需要动规则？改牌桌交互时是否能复用原有规则？用一个固定状态能否验证容量算法？在这个项目中，这些问题的答案都应该是明确的。

## 七、适合小型原生应用的取舍

一个纸牌游戏不需要复杂的服务端架构，也不需要为了“未来扩展”先搭一套通用插件系统。这个项目选择了三个清楚的模块、一套状态模型和一个局部 AppKit 牌桌。功能增加后，再把确实变重的职责继续拆分。

工程结构不是一次性设计出来的完美答案，而是让当前问题容易处理、让后续迭代不互相绊脚的工作边界。下一篇将从另一个容易被忽略的边界开始：牌面素材到底能不能随应用发布，以及视觉设计如何在授权与可读性之间反复打磨。
