# FreeCell 开发实战 FC-11｜从“能玩”到发布：空当接龙项目复盘

**本文目标**：回看这个 FreeCell 项目从规则实现到 GitHub Release 的完整过程，总结哪些问题来自真实试玩、哪些取舍让迭代更稳，以及现阶段仍未覆盖的验证边界。

---

## 一、最初的“完成”太狭窄

最早的目标很容易描述：发出 52 张牌，允许移动，凑齐基础堆。主流程跑通后，真正的产品问题才陆续出现：窗口中牌列太长、拖动时来源牌还留在原地、双击和长按冲突、人像牌在叠放时只露字母、系统 Dock 图标没有显示、用户下载后如何安装。

这些都不是规则引擎的 bug，却直接决定玩家是否觉得游戏完整。项目的完成定义因此从“玩法能跑”扩展到“桌面体验一致、设置可用、资源可合法发布、下载后有明确安装路径”。

## 二、用户截图和试玩反馈很有价值

一些视觉问题很难只靠代码审查发现。用户把牌摊开、叠起来分别观察，指出角标、花色、人像、纸面色调的问题；真实截图让反馈对应到具体牌面状态。牌桌尺寸也经过多轮用户试玩，才形成“牌宽只跟窗口变、长列单独压缩”的布局原则。

输入手势同样如此。单击需要等待双击窗口，鼠标长按跨越间隔后是否还算双击，不容易在抽象规则讨论中发现。只有操作真实应用时，事件时序问题才浮现出来。

## 三、几项对项目质量影响最大的决定

- **规则纯化**：单一规则实现服务点击、拖拽、双击、自动收牌和存档校验。
- **状态与动画分离**：规则状态一次提交，动画只是可取消的展示过程。
- **素材来源可追溯**：每种第三方资源分别记录许可与署名。
- **偏好与牌局分开**：语言变化不应改动游戏进度；坏档无法备份时停写保护原文件。
- **发布脚本化**：构建架构检查、DMG/ZIP、SHA-256 和 Release 附件都可以复现。

这些不是宏大架构，而是针对具体风险建立的小边界。每个决定都能指出它避免了哪一种可见故障。

## 四、后续仍需诚实对待的限制

项目配置 macOS 14 为最低版本，但没有在 macOS 14 实机验证；本机 Release 检查不等于其他 M 系列机型验收。应用使用临时签名，没有 Apple Developer ID 签名与公证，首次下载打开可能需要用户在系统设置中允许。

九种语言的资源完整性和格式化有自动检查，但译文未经过所有语言母语者审校。VoiceOver、不同刷新率设备、长时间游玩、外接显示器和下载后的首次启动仍可增加专门回归。公共 Git 历史里可能保留早期来源不明确的旧牌面，清理历史会改变提交 ID，需要另行决策。

把限制列清楚不是削弱项目，而是告诉玩家与维护者哪些已知、哪些尚待证实。

## 五、如果重新开始，我会更早做什么

第一天就列出素材来源和许可清单，避免主流程完成后才发现资源不能发布。早期就定义固定牌局和验收命令，让规则回归随实现同步增长。更早把“牌宽稳定”和“叠牌可读性”写成可检查约束，减少仅凭主观感受调整。最后，把 DMG 安装、首次启动说明和发布资产核对纳入计划，而非项目收尾阶段的临时工作。

## 六、一个纸牌游戏也能练完整工程能力

FreeCell 不需要后端、数据库或复杂云服务，但它仍然要求建模、规则验证、状态管理、并发保存、原生输入、视觉迭代、可访问性、多语言、第三方许可和软件发行。问题规模不大，却能把一款桌面应用从需求到交付的关键环节串起来。

如果读者从这组文章只带走一个方法，我希望是：把产品体验拆成能观察、能复现、能验证的场景；让核心状态不依赖界面；对发布中的素材、签名和系统兼容保持准确描述。一个项目因此更容易迭代，也更容易让别人放心使用。
