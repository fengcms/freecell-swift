# FreeCell 开发实战 FC-03｜先确认授权，再美化牌面：免费牌面的筛选与视觉迭代

**本文目标**：讲清楚为什么“图片能找到”不等于“可以发布”，以及牌面如何经过多轮真实试玩，从授权、清晰度和叠放可读性三方面达到可交付状态。

---

## 一、发布前才发现的素材问题

项目早期使用了一套来自其他纸牌应用的牌面资源。它们在本机能显示，游戏流程也能正常运行，但“可以从已安装的应用里提取”并不能证明我们有权把图片重新分发给其他玩家。既然目标是公开发布，这就成了阻断发行的问题。

处理方式不是继续猜测授权，而是寻找来源清楚、许可允许修改和再分发的牌面。最终采用 Byron Knoll 的 Vector-Playing-Cards 公共领域素材，并把对应上游提交、原始 SVG、转换后的游戏图片及许可说明保存在仓库中。源码使用 MIT 许可，并不会自动覆盖第三方图片、音乐和图标；每类素材都需要按自己的许可说明。

## 二、素材来源要能被未来的维护者复核

牌面来源写入 `THIRD_PARTY_NOTICES.md`，原始 SVG 保存在 `App/CardSources/`，随应用也会带上相应署名文件。牌图按稳定 ID 对应花色和点数，最后渲染成应用运行时使用的 PNG。

这里有两个容易遗漏的细节。第一，署名文件要进入最终 `.app`，只留在仓库里，下载用户可能看不到。第二，替换工作树中的素材不等于删除 Git 历史里的旧文件；若旧资源曾被提交，它仍可能从旧 commit 下载。历史清理涉及改写 commit ID，需要单独评估与协调，不能假装一次文件替换就完成了。

## 三、单张牌好看，叠起来也要清楚

新的牌面并没有一次定稿。先看整副牌，能发现比例、色彩和花色形状问题；再把牌叠成真实工作列，才会发现角标是否被上一张盖住、人像露出多少、暖色纸面是否过亮。

每轮调整都围绕玩家实际看到的区域：

- 数字与边框留出足够呼吸空间，细字加粗；
- 数字牌中央花色控制大小，避免压过角标；
- 纸面从刺眼纯白改为柔和暖色渐变，并逐轮降低亮度；
- J/Q/K 人像在叠放时露出足够轮廓，完整展示时又不过分突兀；
- 移除人像外围的黑色框线，修正梅花为三瓣形。

这些变化不能仅靠单张 PNG 审美判断。用户提供的叠牌截图非常关键：它把问题从“这张图是不是漂亮”变成“牌局进行时，信息是否仍清晰、整列是否协调”。

## 四、保留原图，生成结果可重复

调整后的源素材与生成资源分开保存。样式脚本负责修改 SVG 结构和颜色，渲染脚本负责把 52 张牌输出为固定尺寸 PNG。重新生成需要 Node.js 和 sharp，但普通构建只需 Swift；这避免把图像处理依赖带给应用用户。

可重复生成还让视觉方案可审查：改动源 SVG 或脚本后，可以重新生成整副牌并查看 contact sheet，而不是手工逐张改图，导致某张牌遗漏或牌面比例不一致。

## 五、素材决策也是产品设计

最终牌面同时满足三件事：许可允许公开分发；52 张牌拥有稳定、可校验的映射；在完整展示和真实叠牌两种状态下都容易辨认。任何一项不成立，视觉再漂亮也不能算完成。

这次迭代最有价值的经验是：素材授权应尽早确认，但视觉验收应进入真实产品状态。单独打开图片只能回答一半问题，另一半要把它放回牌桌、窗口缩放和牌列叠放中验证。
